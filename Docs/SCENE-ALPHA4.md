# Alpha4: scene preparation and recovery repair

The user video showed a first acknowledgement timeout, then a cleanup exception and later exhausted own-handle registration. The exact unready native condition and actual exception site were not identified by the video; this candidate must not call them proven.

Written repairs preserve runtime ABI, event and foreground checks, total own-resource maximum3, iOS15.0+ with no upper gate, working Settings and alpha3 trigger. No device connection/install/respring, merge or Release is authorized.

- A real cancel/progress surface stays available while panes are unready; only pane input is gated, not the entire UIWindow. Native window binding no longer waits behind a globally disabled window. Replacement staging is not hidden behind a zero-alpha ancestor.
- Toolbar layout reserves56pt between real pane frames, and input mode reserves a separate header. No control is placed on an App bottom bar when the gap is insufficient.
- Newly returned but invalid/stale handles are released. Closing invalidates the coordinator generation and invokes bridge releaseAll, covering acquisitions not yet adopted by top/bottom references.
- Active registration and unconfirmed recovery are distinct; total resources remain bounded and recovery blocks new acquisition. Detach precedes presenter invalidation; finally removes active registration even when an individual cleanup step throws. Explicit recovery retry preserves exact original ownership rather than discarding errors or destroying system scenes.
- Every readiness group is read independently; timeout/exception errors carry bounded operation/stage/selector and pending structural labels, not original exception payloads or UI/input content.
- ARC init calls use a consumed receiver/retained result, and ObjC exception cleanup is enabled. This corrects an ownership boundary; no statement is made that it was the exact filmed exception.
- One final error report preserves both the first operation failure and the cleanup result. A native timeout is not “fixed” by lengthening its deadline or removing its required condition.

Cloud verification must directly compile production DXRuntime/DXSystemBridge with test-only class maps and execute100 actual production cleanup fault cycles, cancellation/late callback/duplicate release/partial acquisition/readiness failure and max-resource cases. Those fixtures do not prove real private Scene authority. Separate real UIKit preparation/toolbar and existing Settings/core/C checks are required before native dual-architecture packaging. Logs/artifact SHA and final device limits are recorded only after actual completion.
